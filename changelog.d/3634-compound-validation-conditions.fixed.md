- Model validations: `condition`/`unless` expressions that combine clauses with `&&`/`||` no longer throw `Unsupported operator in condition`. `$evaluateConditionString()` now splits a compound boolean at the top level (quote- and paren-aware, with `&&` binding tighter than `||`) and evaluates each side with the existing single-clause machinery, and it recognises a small whitelist of read-only function calls with arguments, including the idiomatic `StructKeyExists(this, 'property')` and the list predicates `ListFind`/`ListFindNoCase`/`ListContains`/`ListContainsNoCase` (so legacy conditions of the shape `ListFind('a,b,c', this.id)` keep working instead of newly throwing). Previously any such expression fell through to the three-token `$evaluateLogicalExpression()` parser, which read the wrong token as the operator; because 4.1.0 made that path fail closed, the symptom changed from a silently skipped validation to a thrown `Wheels.InvalidValidationCondition` (HTTP 500 on save). The widened grammar also accepts a leading `!` on any supported clause (`!StructKeyExists(this, 'x')`, including inside a compound expression), parenthesised groups (`(a || b) && c`), and symbolic operators (`==`, `!=`) within a compound clause. A whitelisted function argument that names a property absent from the instance now resolves to an empty value instead of throwing, so `StructKeyExists(this, 'a') || StructKeyExists(this, 'b')` short-circuits as written rather than 500ing on the first clause. A whitelisted function called with the wrong number of arguments reports an arity error rather than being described as unsupported. Note: a function-call condition outside the whitelist still throws here whereas 4.1.0 silently returned false — see the PR description for that remaining upgrade hazard (#3634)
