- `enqueue()`, `enqueueIn()` and `enqueueAt()` accept `uniqueKey`: only one job is written per key, including when two enqueues race each other. A duplicate writes nothing and returns `{enqueued: false, duplicate: true, status: "duplicate"}` with the existing job's `id`; a key stays taken while its row exists, until it is purged. Every enqueue result now includes `enqueued` and `duplicate`. `wheels_jobs` gains a nullable `uniqueKey` column (VARCHAR(255)) with a unique index (filtered to non-NULL keys on SQL Server). It is added to existing tables automatically under the migration lock, taken without waiting, and backfilled from `id`; servers still on the previous version keep enqueuing during a rolling upgrade. `enqueue(uniqueKey=...)` throws `Wheels.Job.UniqueKeyUnavailable` when the column can't be added, and `Wheels.Job.InvalidUniqueKey` for a key over 255 characters. ([#4478](https://github.com/wheels-dev/wheels/issues/4478))
