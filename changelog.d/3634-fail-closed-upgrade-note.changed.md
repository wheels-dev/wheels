- **Upgrade note (4.0.x → 4.1.x) — validation `condition`/`unless` expressions now fail closed.** A `condition`/`unless` string that the evaluator cannot parse (a compound `&&`/`||` expression, or a function call with arguments outside the read-only whitelist: `StructKeyExists`, `IsNull`, `IsNumeric`, `IsSimpleValue`, `IsStruct`, `IsArray`, `IsBoolean`, `IsDate`, `Len`, `ListFind`, `ListFindNoCase`, `ListContains`, `ListContainsNoCase`) now throws `Wheels.InvalidValidationCondition` — an HTTP 500 on the save that triggers it. 4.0.x caught the same parse failure and returned `false`, which *skipped* the validation entirely: app authors should treat a 4.1 upgrade as the moment previously-inert validations start being enforced, and audit any `condition`/`unless` that names a property inside a function call. Two real cases surfaced on one production app during the 4.1 upgrade: `condition="StructKeyExists(this, 'requestFor') && this.requestFor == 'Engine Part'"` (500 on every save) and `condition="ListFind('24,32,63,67,117,167,191', this.countryId)"` (silently inert — the validation never ran). Fail-closed is deliberate: silently skipping a validation hides data-integrity holes, which is exactly how both of those survived for years. `wheels-dev/wheels#3634` (#3634)
