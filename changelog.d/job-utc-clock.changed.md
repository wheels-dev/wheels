- Background-job timestamps (`runAt`, `createdAt`, `updatedAt`, `completedAt`, `failedAt`, `heartbeatAt`, and the host registry's times) are now stored in UTC, read from the database's own clock, so every server that shares the job tables uses one clock: a server whose clock runs ahead or behind no longer reaps a live job early or picks up a delayed job late. The database's UTC time is read at most once a minute per application (about one-second precision); if a read fails the last good reading is kept. Timestamps are built by the database from integers, so servers in time zones with daylight saving are handled across the clock changes. H2 and SQLite use the server's own clock (both are single-host databases). **H2 requires the JVM to run on UTC:** H2 1.4 does timestamp arithmetic in the JVM's time zone. The API stays in local time: `enqueueAt()` takes a local date/time, and `JobRunner.status()` and the queue stats report local times. **Upgrading:** on SQL Server, MySQL, PostgreSQL, CockroachDB, Oracle and H2, rows written before this release hold the server's local time, so on servers that don't run in UTC either upgrade once the queue is empty (no pending or processing jobs; otherwise a delayed job runs early or late by the offset, and on a server behind UTC an in-flight job looks stale and is reclaimed), or set `this.convertLocalOffsetMinutes` in the `wheels jobs install` migration to the old servers' offset from UTC to convert existing rows once (in one transaction; running it again changes nothing). SQLite rows and servers already running in UTC need neither.
