- Added `afterCommit` and `afterRollback` model callbacks. `afterCommit(methods, on)` runs its methods only after the database transaction actually **commits** — the right place for side effects that must not happen on a rollback (enqueue a job, send mail, bust a cache, call an external API). `afterRollback(methods, on)` runs when the transaction **rolls back**. Both cover `create`, `update`, and `delete`, support an optional `on="create,update,delete"` filter, and (for nested writes or an `invokeWithTransaction` block) fire once, together, when the **outermost** transaction resolves. With no transaction (`transactionMode="none"`) `afterCommit` fires immediately after each write. A callback that throws runs after the commit, so the commit stands; the error is logged to `wheels.log` and propagated. These callbacks require a Wheels-managed transaction (`transaction()` / `invokeWithTransaction`): a write placed inside a raw CFML `transaction {}` block is skipped (with a one-time `wheels.log` warning) on Lucee and BoxLang, and is not detectable on Adobe CF or RustCFML — there the behaviour inside a raw `transaction {}` is left to the engine and is not guaranteed.
