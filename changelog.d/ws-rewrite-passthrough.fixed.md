- WebSocket upgrades to `/ws/<name>` now reach [lucee/extension-websocket](https://github.com/lucee/extension-websocket) (used by the `wheels-websockets` package at `/ws/wheels`) under the `wheels new` Tomcat rewrite rules and the `wheels deploy init` Dockerfile. Previously the front-controller catch-all rewrote the upgrade to `/index.cfm/ws/...` before Tomcat's WsFilter could match the endpoint, so the client got a Wheels 404 instead of a `101`. The new pass-through is gated on the `Upgrade: websocket` header, so ordinary HTTP routes under `/ws/` keep reaching the router. **Existing apps are not updated automatically** — `wheels start` only copies the template into a project that has no `rewrite.config`. Add these two lines to your project-root `rewrite.config` just above the `# Route everything else through the front controller` rule (or, if you never customised the file, delete it and `wheels start` regenerates it from the new template); apps deployed with a Dockerfile from `wheels deploy init` need the same two lines added to the `printf` rule list before `'RewriteRule ^/(.*)$ /index.cfm/$1 [L]'`:
  ```
  RewriteCond %{HTTP:Upgrade} ^websocket$ [NC]
  RewriteRule ^/ws/.*$ - [L]
  ```
  CommandBox/Undertow (`urlrewrite.xml`) is unchanged: on Undertow the extension accepts the upgrade but never runs the listener, so there is no working WebSocket path there yet (wheels-dev/wheels-websockets#1)
