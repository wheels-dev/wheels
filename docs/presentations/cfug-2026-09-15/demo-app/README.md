# Demo app reference

Reference model configs and **optional deterministic seeds** for the
eight-beat build in [`../demo.md`](../demo.md). This is not a complete app:
create the app, migrations, controllers, views and specs with the CLI.

## Model configs

- [`Post.cfc`](Post.cfc): generated title/body/publishedAt presence and title
  maximum, plus the live `Untitled` exclusion and comments association.
- [`Comment.cfc`](Comment.cfc): belongsTo post and generated body/post_id
  presence. There is no author column in this demo.

Compare `config()` with your generated app, not entire file bytes:
generator version/date headers, quote style and ordering may differ.
Keep the generated validations when adding the live business rule. Restore
Post's body presence after the deliberate red/green exercise. Neither
reference promises cascading deletion; `hasMany` does not imply it.

## Main presentation: generated sample data

The PowerPoint's normal track uses `wheels seed --generate`: ten Posts
first, then ten Comments **and another ten Posts** after the Comment
scaffold. It does not use these convention seed files. Preserve Post IDs
1–10 on the rehearsed build and check for orphans; autogenerated integer
FKs are not a lookup of real parent IDs. Keep **Hello, Wheels** for the
later query-builder search.

## Deterministic recovery / small-data track

Set `TALK_ASSETS` to the absolute presentation directory as described in
the runbook. From the generated app, after the **Post migration only**:

```bash
mkdir -p app/db
cp "$TALK_ASSETS/demo-app/seeds.cfm" app/db/seeds.cfm
wheels seed --mode=convention
wheels seed --mode=convention
```

[`seeds.cfm`](seeds.cfm) supplies two Posts with fixed publication dates and
uses `seedOnce` keyed by title. From empty tables expect two created, then
two skipped. Existing matching Posts are preserved, not updated.

After the **Comment migration**, replace the seed with the standalone
parent-and-child example:

```bash
cp "$TALK_ASSETS/demo-app/seeds-with-comments.cfm" app/db/seeds.cfm
wheels seed --mode=convention
wheels seed --mode=convention
```

[`seeds-with-comments.cfm`](seeds-with-comments.cfm) includes both parent
seeds, resolves their **actual IDs by title**, then seeds one Comment on
each with `uniqueProperties="post_id,body"`. From the two-Post state expect
two Comments created and two Posts skipped; repeat should skip all four.
From empty Post/Comment tables expect four created, then four skipped.
Verify persisted counts and zero orphans rather than relying only on an
exit code. Test this fallback separately from the main generated-seed run.
The independent build-2482 recipe rehearsal measured the staged clean
flow: Post-only **2 created / 0 skipped**, repeat **0 / 2**; parent IDs then
changed to **41/97** before any children existed; parent-and-child seed
**2 / 2**, repeat **0 / 4**. Final database: two Posts, two Comments using
41/97, zero orphans, **20 passing specs**. Both files were also repeated on
a prepopulated app without adding duplicate seed records. Running the
combined file directly on entirely empty Post/Comment tables was not a
separate measured run.

If the database already contains duplicate Posts with either title,
resolve the duplicates first: `seedOnce` does not deduplicate existing
rows. Use actual IDs in console commands on this track; `/posts/1` and
Comment 3 are not guaranteed. There is no auth-model coupling in either
seed file. To create Comments interactively instead, select a real Post
in the generated form.

`wheels seed` auto-detects convention files; `--generate` bypasses them.
Do not seed two parents with these files and then assume generated child
FKs 1–10 are valid. LuCLI has no `wheels generate seed` command;
`wheels generate snippets seed-data` produces other example files that
must be copied into place before use. Both seed modes need the running
server for the current project.
