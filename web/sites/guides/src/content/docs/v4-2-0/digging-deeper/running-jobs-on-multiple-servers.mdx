[Background Jobs](/v4-2-0/digging-deeper/background-jobs/) shows you how to define, enqueue, and process jobs with one worker. This page is what changes when **several app servers share one `wheels_jobs` table** and all of them process it — the usual shape behind a load balancer. The queue is a database table, so adding servers needs no broker and no new infrastructure; what it needs is a clear idea of the guarantees you get, the two things your job code must do, and one schema change to make on the database before the servers go live.

**You'll learn:**

- What running across servers guarantees — and what it asks of your `perform()`
- How a job records liveness with `heartbeat()`, why `timeout` is a hard cap, and what `Wheels.Job.Fenced` means
- How `this.idempotent` chooses at-least-once or at-most-once recovery
- How lifecycle hooks and an app-wide failure hook let you observe jobs running on other servers
- How to cap how many jobs one server runs at once
- How to make a job exclusive, or one-per-key, across the whole fleet
- How to run the queue: a CLI worker, a process supervisor, or a scheduled task
- How to declare recurring schedules that produce one job per slot across the fleet
- How to drain a server before a deploy so it finishes its work and stops cleanly
- Which schema to apply yourself, rather than let a live server alter the table
- Why every server must agree on the time

  Read [Background Jobs](/v4-2-0/digging-deeper/background-jobs/) first. This page assumes you know how to define a job, enqueue it, and process the queue with `wheels jobs work` or `processQueue()`. It builds on those; it doesn't repeat them.
</Aside>

## The guarantees

Several workers polling the same table is safe by design: each job is claimed with an atomic, guarded `UPDATE` (`WHERE id = :id AND status = 'pending'`), so two workers never start the same row. Beyond that, 4.2 makes the recovery path safe when a worker dies or stalls mid-job. The guarantees are worth stating exactly, because the two things they ask of your code follow directly from them.

- **One job runs on one worker at a time.** The claim is atomic. A row in `processing` is owned by whichever worker claimed it.
- **A crashed worker's job is recovered.** A worker killed mid-run leaves its row stranded in `processing`; the next poll on that queue reaps it (past a grace margin built from the claiming worker's own `timeout`) and requeues it for retry, or fails it once retries are exhausted. This is covered in full under [Crashed workers and the `timeout`](/v4-2-0/digging-deeper/background-jobs/#crashed-workers-and-the-timeout).
- **One recorded *outcome* per attempt — not one execution.** A worker that was only stalled (a long GC pause, a hung remote call) can come back to life after its job was reaped and claimed again. Every claim writes a fresh `claimToken` to the row, and a worker may only complete, retry, or fail a job while the row still carries *its* token. The late attempt's result is discarded and logged as `Wheels.Job.Fenced`. Its `perform()` still ran to the point it stalled, though — so the work may have happened twice even though only one outcome was recorded.

Two consequences for your code:

1. **`perform()` must be idempotent.** Recovery is at-least-once: a reaped job runs again, and a fenced attempt already did part of its work. Write `perform()` so running it twice is the same as running it once — check-before-write, store an idempotency key, lean on a unique database constraint. This is the single most important rule for jobs on more than one server.
2. **The guarantees hold only once every worker is on 4.2.** Fencing lives in the claim and the terminal updates. A worker still on 4.1 claims and completes a job *without* a token, so it can still overwrite a newer attempt. During a rolling upgrade, expect the old behaviour until the last 4.1 worker is gone. Jobs already `processing` when a worker upgrades have no token and are reaped the old way.

<Aside type="caution" title="Enqueue once, across servers">
When several servers (or several requests) might enqueue the *same* piece of work — a nightly report, a per-record follow-up — give the job a `uniqueKey` so only one row is written, whichever server gets there first. It's the natural companion to processing on many servers. See [Enqueue at most once with `uniqueKey`](/v4-2-0/digging-deeper/background-jobs/#enqueue-at-most-once-with-uniquekey).
</Aside>

## Record liveness with `heartbeat()`

A job's `timeout` is a **hard cap on a single attempt**: `perform()` runs in a bounded thread and is stopped when the timeout elapses, however much work is left (the attempt is then retried or failed like any timeout). `heartbeat()` does **not** extend that cap — a job can't run past its `timeout`. What it does is record that this attempt is *alive*: call it from inside `perform()` as the work proceeds, and it stamps the row's liveness for the reaper to read.

```cfm {test:compile} title="app/jobs/RebuildSearchIndexJob.cfc"
component extends="wheels.Job" {
    function config() {
        super.config();
        this.queue = "maintenance";
        this.timeout = 120;   // a batch should take well under two minutes
    }

    public void function perform(struct data = {}) {
        var job = this;
        var onBatch = function(batch) {
            reindex(batch);
            job.heartbeat();   // "still alive" — stamps liveness for the reaper (doesn't extend the timeout)
        };
        model("Product").findInBatches(batchSize = 500, callback = onBatch);
    }
}
```

`heartbeat()` stamps liveness on **this attempt's claim only** (it carries the same `claimToken` guard as a completion). Call it between units of work — after each batch, each file, each page — not in a tight inner loop.

If the claim is gone — the job was already reaped and handed to another worker while this one stalled — `heartbeat()` throws `Wheels.Job.Fenced`. That's your signal to **stop and return from `perform()`**: another attempt owns the job now, and anything more this attempt does will be discarded. Let the exception propagate; don't catch it to keep working.

<Aside type="note" title="What liveness does today, and what's coming">
`heartbeat()` also renews an [exclusive or concurrency-keyed job's](#exclusive-jobs-and-concurrency-keys) lease, extending it with each beat. Like its effect on the reaper, this is mostly groundwork today: because `timeout` hard-caps each attempt and the lease is sized to outlast that, the lease can't expire mid-run as things stand, and [#4502](https://github.com/wheels-dev/wheels/issues/4502) will make a heartbeating long job detectable as dead sooner when its worker actually dies. Either way, `heartbeat()` never extends the per-attempt `timeout`.
</Aside>

<Aside type="note" title="Restricted database users">
`heartbeat()` stamps a `wheels_jobs.heartbeatAt` column. On a table whose database user can't `ALTER` it, the column is absent and `heartbeat()` stamps `updatedAt` instead — still correct, just coarser. See [The shared schema](#the-shared-schema) to add the column once by hand.
</Aside>

## Idempotency and `this.idempotent`

Some work genuinely must not run twice, and can't be made idempotent — a job that posts to a ledger, say, where a replay is a real double-post. For those, `this.idempotent` changes what happens when a reaped job's worker is presumed dead:

```cfm {test:compile} title="app/jobs/PostLedgerEntryJob.cfc"
component extends="wheels.Job" {
    function config() {
        super.config();
        this.queue = "ledger";
        this.idempotent = false;   // do NOT re-run after a reap
    }

    public void function perform(struct data = {}) {
        // A replay here would double-post. Better to stop than to risk it.
        postEntry(arguments.data.entryId);
    }
}
```

- `this.idempotent = true` (the **default**) — recovery is **at-least-once**. A reaped job is retried, the attempt counts against `maxRetries`, and your idempotent `perform()` absorbs the replay. This is what every job does unless you say otherwise.
- `this.idempotent = false` — recovery is **at-most-once**. A reaped attempt is **not** re-run: the row ends in the new status `interrupted`, and stops there. You've chosen "didn't finish" over "might run twice".

`interrupted` rows are counted in `queueStats()` and `getStats()` alongside `pending` / `processing` / `completed` / `failed`, so you can alert on them:

```cfm {test:compile} title="watch for interrupted work"
component extends="Controller" {
    function metrics() {
        var jobs = new wheels.Job();
        var stats = jobs.queueStats();
        // {pending, processing, completed, failed, interrupted, total}
        renderWith(data = stats);
    }
}
```

An `interrupted` row is a job that may not have finished and deliberately won't be retried, so treat a non-zero `interrupted` count as something to look at — decide per entry whether the work needs re-queuing by hand. Like `failed` rows, `interrupted` rows persist (`purgeCompleted()` only touches `completed` rows). Once you've dealt with them, clear the old ones with `purge()`:

```cfm {test:compile} title="prune interrupted rows"
new wheels.JobWorker().purge(status = "interrupted", days = 30);   // interrupted rows older than 30 days
```

`purge(status, days, queue)` accepts `"completed"`, `"failed"`, or `"interrupted"`, so it's also how you prune failed rows once you've extracted what you need from `lastError`.

## Lifecycle hooks and failure handling

A job can hook its own lifecycle, and the application can hear every failure in one place — which matters across servers, where a job you enqueued runs on a machine you aren't watching.

```cfm {test:compile} title="app/jobs/ChargeCardJob.cfc"
component extends="wheels.Job" {
    public void function perform(struct data = {}) {
        order = model("Order").findByKey(arguments.data.orderId);
        order.chargeCard();
    }

    // Best-effort, after the outcome is recorded:
    public void function onSuccess(any result) { /* ... */ }
    public void function onFailure(any error, numeric attempt, boolean isFinal) {
        if (arguments.isFinal) notifyBilling(arguments.error);   // gave up for good
    }
}
```

Per-job hooks, all optional:

- **`beforePerform(data)`** and **`afterPerform(data, result)`** run *as part of the work* — inside `perform()`'s timeout, on the same attempt. A throw from either **fails the attempt**, like a throw from `perform()`. Use them for setup and teardown that must succeed for the job to count.
- **`onSuccess(result)`** runs once the completion is recorded, and **`onFailure(error, attempt, isFinal)`** after each recorded failure. Both are **best-effort**: a throw is logged, not propagated, and never changes the recorded outcome.

`isFinal` is `true` when the job won't be tried again — the last retry failed, **or** a reaper gave up on it: a reaped last attempt, and a non-idempotent job the reaper ends as `interrupted` (see [Idempotency](#idempotency-and-thisidempotent)), both fire `onFailure(..., isFinal = true)`. So `onFailure` with `isFinal` is a reliable "this job is done trying" signal even when the giving-up happened on another server's reaper, not in `perform()`.

For centralized alerting, set an **application-wide failure hook** that hears every job's failures:

```cfm {test:compile} title="config/settings.cfm"
set(jobsOnFailure = "app.jobs.FailureNotifier.report");
```

It's called on every recorded failure with one struct — `{jobId, jobClass, queue, attempt, maxRetries, isFinal, error}`. It deliberately carries **no job `data`** (that can hold secrets), so it's safe to route to logs or an alerting service.

### The stored result

`perform()`'s return value is stored on the row, in a `wheels_jobs.result` column, and handed to `onSuccess(result)`. A simple value is stored as-is; a struct or array is stored as JSON. It's capped at 4000 characters (bound as `NVARCHAR` on SQL Server, UTF-8 bytes elsewhere), truncated on a character boundary with a visible marker if it's longer — so return a small summary, not a large payload. The `result` column is added by the same guarded auto-`ALTER` as the other 4.2 columns; without it, jobs run exactly as before and nothing is stored.

## Cap how many jobs a server runs at once

By default a server runs as many jobs as its workers claim. To bound the load one server puts on a shared database or an external API, set a per-host cap:

```cfm {test:compile} title="config/settings.cfm"
set(jobsMaxConcurrentPerHost = 4);   // this server runs at most 4 jobs at once; 0 (default) = no cap
```

The cap is enforced by every runner that goes through the worker — the CLI worker (`wheels jobs work`), `JobRunner.tick()`, and `processQueue()` (which runs through the worker as of [#4495](https://github.com/wheels-dev/wheels/issues/4495)). A server at its cap claims nothing new until a running job finishes; other servers keep working to their own caps. The count is per *host*, so the cap governs all the workers and pollers on one server together, not each process on its own.

<Aside type="note" title="What counts as a host">
A host is the name a worker records in `wheels_jobs.claimedBy` — the machine's host name by default. When several app servers (JVMs) run on one machine, or you want several processes to share one cap and one drain flag, name each explicitly with `set(jobsHostName = "web-1")`. Two processes with the same host name share a cap; two with different names don't.
</Aside>

## Exclusive jobs and concurrency keys

The per-host cap bounds *how many* jobs a server runs. A different need is making sure two runs of a *particular* job never overlap across the whole fleet — a nightly billing run that must not double, a per-account sync that mustn't race itself. Declare that in the job class:

```cfm {test:compile} title="app/jobs/NightlyBillingJob.cfc"
component extends="wheels.Job" {
    function config() {
        super.config();
        this.exclusive = true;   // at most one run of this class at a time, across all servers
    }
    public void function perform(struct data = {}) {
        runBilling();
    }
}
```

- **`this.exclusive = true`** (default `false`) — at most one run of this job class at a time, on any server. While a run holds it, another server that claims the same class puts the job **back to `pending`** (its attempt is handed back, not spent) and tries again once the lease frees.
- **`this.concurrencyKey = "..."`** — instead of locking the whole class, share one lease among jobs with the same key. Two jobs with different keys run concurrently; two with the same key don't.
- **`concurrencyKeyFor(struct data)`** — a key computed from the job's data, for per-record exclusion. It **wins over** `this.concurrencyKey` when both are set:

```cfm {test:compile} title="app/jobs/SyncAccountJob.cfc"
component extends="wheels.Job" {
    public string function concurrencyKeyFor(struct data = {}) {
        return "account:" & arguments.data.accountId;   // one sync per account at a time
    }
    public void function perform(struct data = {}) {
        syncAccount(arguments.data.accountId);
    }
}
```

The lease lives in a `wheels_job_locks` table (auto-created on first use, never inside a transaction), owned by the running attempt's claim token, and lasts as long as the attempt's reap window — the timeout it was claimed with plus the reap grace — so it covers the run. A long run can [`heartbeat()`](#record-liveness-with-heartbeat) to extend the lease as it goes. If a run does lose its lease before it finishes — taken over after expiry — that's logged and counted (as `leasesLost` in a `processQueue()` result), and the run is **not** failed for it; make the work idempotent so a rare overlap is harmless.

<Aside type="caution">
A busy lease is retried, not dropped, so an exclusive job that always finds its lease held (a run that never ends, a key that's too coarse) will keep being put back to `pending` and never make progress. Scope `concurrencyKeyFor()` as narrowly as correctness allows, and make sure exclusive jobs actually finish.
</Aside>

## Running the queue on each server

[Background Jobs](/v4-2-0/digging-deeper/background-jobs/#process-the-queue) covers the two ways to process the queue. Across servers, run one of them on **each** server; they coordinate through the shared table.

- **The CLI worker** — `wheels jobs work` under a process supervisor (systemd, Docker's restart policy, a Kamal accessory). When it loses its app server it exits non-zero and the supervisor restarts it. Run one (or several) per app server. This is the simplest option and the one to reach for first.
- **A scheduled `processQueue()`** — call `processQueue()` from a CFML scheduled task or a cron-invoked script on each server, at whatever cadence your latency allows. No long-lived process to supervise. As of [#4495](https://github.com/wheels-dev/wheels/issues/4495) it runs through the worker, so it reaps stale jobs first, honours the per-host cap, and stops starting new jobs on a draining host — the same safety as the CLI worker. (It doesn't refresh the server's `lastSeenAt` / code version in the host registry the way `tick()` does, but its running count and drain state are read live, so `wheels jobs status` and `wheels jobs drain --wait` still see its in-flight jobs.)
- **`JobRunner.tick()`** — one call that registers the server in the host registry, reaps stale jobs, and runs a bounded batch, all honouring the per-host cap and drain flag. It's the right building block for a scheduled task, because it keeps the host registry (and so `wheels jobs status` and drain-aware deploys) current:

```cfm {test:compile} title="a scheduled task on each server"
// Run every minute from a CFML scheduled task or a cron-invoked script.
new wheels.JobRunner().tick(
    queues = "default,mailers",   // empty = all queues
    maxConcurrent = 2,            // -1 (default) uses set(jobsMaxConcurrentPerHost); 0 = no cap
    timeout = 300,               // seconds a single job may run
    maxJobs = 5                  // most jobs to run in this tick
);
```

`tick()` runs its jobs synchronously, one after another, and does nothing beyond the cap or while the host is draining. Run it as often as your latency target wants; each call does a bounded amount of work and returns.

<Aside type="note" title="Planned: a token-gated HTTP tick">
An engine scheduled task that can only make an HTTP request — rather than run CFML directly — will be able to drive `tick()` through a token-gated `/wheels/jobs/tick` route, so you can schedule the queue from the engine's own task scheduler. That route is **not built yet** ([#4482](https://github.com/wheels-dev/wheels/issues/4482)); until it lands, drive `tick()` from a scheduled task that runs CFML, as above.
</Aside>

## Recurring schedules

Everything above runs a job *once*. For work that recurs — a nightly digest, a health check every fifteen minutes — declare a schedule. On several servers this is where deduplication would normally bite (every server's cron fires the same minute); the scheduler handles it for you, producing **one job per time slot** no matter how many servers run it.

Declare schedules in `config/schedules.cfm` with a small DSL (`wheels new` doesn't create the file — add it when you need one):

```cfm title="config/schedules.cfm"
schedule("digest")
    .job("DigestJob")
    .cron("0 7 * * MON")
    .timezone("America/New_York");

schedule("health-check")
    .job("HealthCheckJob")
    .every(15, "minutes")
    .queue("maintenance");
```

- **`.job(class)`** — the job class under `app/jobs/`, as for `enqueue`.
- **`.cron(expression)`** — a standard 5-field cron expression (`minute hour day-of-month month day-of-week`), read in the schedule's time zone. Lists, ranges, steps (`*/5`), and names (`MON`, `JAN`) work, as do the `@hourly` … `@yearly` aliases. Seconds and Quartz extensions are refused.
- **`.every(count, "minutes" | "hours")`** — a fixed interval, aligned to the epoch. For a daily or longer cadence, use `.cron()` instead.
- **`.timezone(zone)`** — the IANA zone `.cron()` is read in (default `UTC`), e.g. `Europe/London`.
- **`.catchUp(mode)`**, **`.catchUpWindow(seconds)`**, **`.queue()`**, **`.priority()`**, **`.data(struct)`**, **`.enabled(boolean)`** — tune catch-up (below), and set the same options you'd pass to `enqueue`.

### Running the schedules

Schedules don't run themselves. Call `enqueueDue()` regularly — from a scheduled task, or right next to your job worker — and it enqueues each schedule whose slot has come due:

```cfm {test:compile} title="run the schedules (every minute)"
new wheels.JobScheduler().enqueueDue();
// {checked, enqueued, duplicates, skipped, errors}
```

Each due slot is enqueued with a `uniqueKey` of `"<schedule>:<slot time in UTC>"`, so **you can call `enqueueDue()` on every server** and still get exactly one job per slot — the duplicates land as `duplicate: true` and are counted, not run (this rests on the [`uniqueKey`](/v4-2-0/digging-deeper/background-jobs/#enqueue-at-most-once-with-uniquekey) dedupe). The enqueued jobs are then processed like any other, by whatever is draining the queue. Run `enqueueDue()` about once a minute; it's cheap when nothing is due.

<Aside type="note" title="Planned: automatic schedule runner">
A follow-up in 4.2 (the schedule-runner wiring) calls `enqueueDue()` for you: `JobRunner.tick()` and the CLI worker's poll will check schedules every `jobsScheduleCheckSeconds` (default 30), so `wheels jobs work` and a `tick()` loop fire schedules without a separate call. It's **not built yet** — until it lands, call `enqueueDue()` yourself as above. Once it does, declaring a schedule in `config/schedules.cfm` is all a running worker needs.
</Aside>

### Catch-up: missed slots

If nothing calls `enqueueDue()` for a while — a deploy, an outage — slots are missed. `catchUp` decides what happens when it runs again:

- **`"latest"`** (the default) — run only the **newest** missed slot, and only if it's within `catchUpWindow` (default 3600 seconds). Older missed slots are skipped. This is what you want for an idempotent digest: you get one run, not a backlog.
- **`"none"`** — run a slot only if it's current; never a missed one.

Either way, a slot at or before the last one already enqueued never runs again, and a brand-new schedule starts from *now* — it doesn't fire slots from before it existed. Keep `catchUpWindow` below your [purge retention](#idempotency-and-thisidempotent) so a caught-up slot's `uniqueKey` row still exists to dedupe against.

### Where schedules live

Schedules are rows in a `wheels_job_schedules` table (auto-created on first use, never inside a transaction). `config/schedules.cfm` is synced into it at application start as *code* schedules: edit the file and restart, and the table follows. A code schedule you remove from the file is **disabled, not deleted**, so its history survives. An app can also insert its own rows at runtime (for example from an admin page) as *db* schedules; the start-up sync never touches those, and on a name clash the db row wins.

<Aside type="note" title="Time zones need java.time">
Non-UTC zones use the JVM's `java.time`. A UTC schedule works everywhere; a non-UTC one on an engine without `java.time` is refused with `Wheels.Job.InvalidSchedule` rather than computed wrongly. Around a DST change, a local time the clock skips runs at the next valid instant, and a local time that repeats runs once, at its first occurrence.
</Aside>

## Drain a server before a deploy

The problem a rolling deploy creates: you need to stop a server, but it may be running jobs. Killing it mid-job strands that work (it's reaped and retried elsewhere, but only after its timeout). `wheels jobs work --stop-when-empty` stops one worker loop, not the server, and not any other worker on it. **Draining** is the clean answer: mark the server so it starts nothing new, let its running jobs finish, then stop it.

<Steps>

1. **Drain the server, and wait for it to go quiet:**

   ```bash title="on the server you're about to deploy"
   wheels jobs drain --wait
   ```

   `drain` marks this server draining in the host registry: it starts no new jobs, while jobs already running finish and stale-job reaping continues. `--wait` then polls until the server has no running jobs and exits `0` — at which point it's safe to stop. If jobs are still running when the wait runs out (`--wait` alone allows 600 seconds; `--wait=120` sets your own limit), it exits non-zero so your deploy script can wait longer or investigate rather than stop mid-job.

2. **Deploy** — stop the server, roll out the new build, start it.

3. **Resume**, so the server takes jobs again:

   ```bash title="after the new build is up"
   wheels jobs resume
   ```

</Steps>

A drain lifts itself after `--expires=<seconds>` (default 3600) even if nothing resumes it, so a deploy that dies between `drain` and `resume` doesn't leave the server idle forever. Pass `--expires=0` to drain until an explicit `resume`. The same actions are available in CFML for a scripted deploy — `new wheels.JobRunner().drain(expiresInSeconds = 600)` and `.resume()` — and `status()` (or `wheels jobs status`) reports a server's running count, cap, and drain state from its registry row.

<Aside type="note" title="The host registry">
Drain state lives in a `wheels_job_hosts` table — one row per host, carrying its last-seen time, running count, configured cap, drain flag and expiry, and a code version. It's auto-created on first use (never inside a transaction). The code version defaults to the Wheels version; set your own (a release tag or git SHA) with `set(jobsCodeVersion = "...")` so `wheels jobs status` shows which build each server is running during a rollout.
</Aside>

## The shared schema

The jobs table [auto-creates on first use](/v4-2-0/digging-deeper/background-jobs/#the-jobs-table), and the multi-server columns are added to an existing table the same way — a guarded `ALTER`, run once, outside any transaction. That's convenient on a single server. **On several servers sharing a production database, apply the schema yourself before the servers go live**, for two reasons:

- An auto-`ALTER` runs when the first upgraded server happens to poll, against a live, in-use table. On PostgreSQL and CockroachDB especially, you want that DDL to run on *your* schedule, in a maintenance window, not at an arbitrary moment under load.
- If the application's database user lacks `ALTER` privilege — a common production hardening — the auto-upgrade can't run at all, and the features that need the columns quietly fall back (unfenced claims, `updatedAt` heartbeats). Applying the schema with a privileged user once removes that gap.

The columns the multi-server guarantees use, on the `wheels_jobs` table:

| Column | Type | Used for |
|---|---|---|
| `claimTimeout` | `INT` | Reaping a stale job on the *claiming* worker's timeout, so workers with different timeouts can share a queue |
| `claimToken` | `VARCHAR(36)` | Fencing — a terminal update only lands while the row still carries the attempt's token |
| `claimedBy` | `VARCHAR(128)` | The host that owns a claim (and the per-host cap and drain) |
| `heartbeatAt` | `DATETIME` / `TIMESTAMP` | `heartbeat()` stamping a long job's liveness |
| `uniqueKey` | `VARCHAR(255)` | Enqueue-once dedupe (nullable, with a unique index) |
| `result` | `VARCHAR(4000)` | `perform()`'s stored return value (`NVARCHAR(4000)` on SQL Server) |

Adjust types per database. `heartbeatAt` is a timestamp column, so it's `DATETIME` on MySQL, SQL Server, and SQLite but **`TIMESTAMP` on PostgreSQL, CockroachDB, Oracle, and H2** (PostgreSQL and CockroachDB have no `DATETIME` type). SQL Server omits `COLUMN`; Oracle uses `VARCHAR2` for the string columns and the `ADD (col TYPE)` form. For MySQL (and SQLite, which ignores the exact spelling):

```sql
ALTER TABLE wheels_jobs ADD COLUMN claimTimeout INT;
ALTER TABLE wheels_jobs ADD COLUMN claimToken VARCHAR(36);
ALTER TABLE wheels_jobs ADD COLUMN claimedBy VARCHAR(128);
ALTER TABLE wheels_jobs ADD COLUMN heartbeatAt DATETIME;      -- TIMESTAMP on PostgreSQL / CockroachDB / Oracle / H2
ALTER TABLE wheels_jobs ADD COLUMN uniqueKey VARCHAR(255);
ALTER TABLE wheels_jobs ADD COLUMN result VARCHAR(4000);       -- NVARCHAR(4000) on SQL Server
UPDATE wheels_jobs SET uniqueKey = id;
CREATE UNIQUE INDEX idx_wjobs_unique_key ON wheels_jobs (uniqueKey);
```

On PostgreSQL and CockroachDB, write `ADD COLUMN heartbeatAt TIMESTAMP`. On SQL Server, make the unique index filtered — `CREATE UNIQUE INDEX idx_wjobs_unique_key ON wheels_jobs (uniqueKey) WHERE uniqueKey IS NOT NULL` — because SQL Server allows only one NULL in a plain unique index. The filtered index needs SQL Server **compatibility level 100 or higher**; below that it can't be built. On such a database, either raise the compatibility level, or create a *plain* unique index (no `WHERE`) — but only **once every server runs 4.2** (and so always writes a key), because a plain unique index allows just one NULL and a server still on 4.1 writes NULL keys that would collide. When the framework's own upgrade can't build the index, its warning and the `Wheels.Job.UniqueKeyUnavailable` error now name the failed step and give the fix for your exact database and SQL Server level. On a large, busy table, do the `uniqueKey` backfill and index build in a maintenance window: it touches every row. See [The jobs table](/v4-2-0/digging-deeper/background-jobs/#the-jobs-table) for the full column list and the per-database notes. The auxiliary tables — `wheels_job_hosts` (the host registry), `wheels_job_locks` (exclusive-job leases), and `wheels_job_schedules` (recurring schedules) — have no backfill and are cheap to auto-create, so you can leave those to the framework; only the `wheels_jobs` column changes above are worth applying by hand up front.

<Aside type="note" title="Planned: a schema command">
A `wheels jobs install` command and a `jobsAutoCreateTables` setting — so you can apply the schema from the CLI and turn the auto-`ALTER` off entirely on production — are **planned, not built yet** ([#4499](https://github.com/wheels-dev/wheels/issues/4499)). Until then, apply the DDL above by hand.
</Aside>

## Clocks and skew

All job timestamps — reap windows, heartbeats, `runAt` comparisons — are currently written and compared with **each server's own application clock** (`Now()`), not the database's. If two servers disagree about the time, a job can look stale to one and fresh to another. Keep every app server's clock in sync (NTP, or your platform's time service); a few seconds of skew is harmless, minutes are not.

<Aside type="note" title="Planned: a single database clock">
Writing and comparing all job timestamps on one UTC database clock — removing app-server skew from the reaper entirely — is **planned, not built yet** ([#4486](https://github.com/wheels-dev/wheels/issues/4486)). Until it lands, NTP on every app server is what keeps the reaper honest.
</Aside>

## Upgrading from 4.1

All of this is additive: existing jobs keep working, the new settings default to today's behaviour, and the schema is added for you on first use. The one rule that matters during a rolling upgrade is that **fencing only holds once every worker is on 4.2** — so expect the old recovery behaviour until the last 4.1 worker is gone. The job-related entries on the [4.1 → 4.2 upgrade guide](/v4-2-0/upgrading/4x-1-to-4x-2/) cover each change, the columns added, and what fails safe if skipped.
